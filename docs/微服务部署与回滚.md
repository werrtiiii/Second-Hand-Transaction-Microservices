# 微服务部署与回滚

## 1. 环境隔离与凭证

所有脚本固定使用`secondhand-microservices`命名空间/Compose项目，不操作原单体环境。三个运行账号分别只有本库DML；三个迁移账号仅有本库DDL/DML。每个服务只持有自己的RSA私钥，公钥可共享。

`.env`、私钥、实际数据库密码和kubeconfig不进入Git、Docker构建上下文或交付包。先完成根Maven构建，再执行`GenerateDevEnvironment`生成本地凭证。管理员需显式设置`ADMIN_BOOTSTRAP_ENABLED=true`、手机号和至少12位密码；初始化不会把第一个普通用户提权，也不会覆盖已有普通账号。

## 2. 本地Compose

```powershell
./scripts/deploy-microservices-local.ps1 -Version dev-001
./scripts/rollback-microservices-local.ps1 -Version dev-001
```

部署会检查所有服务就绪、运行三条网关业务冒烟并核验版本。失败返回非零且保存日志到`reports/local-runtime/`。本地回滚只使用已存在的镜像，不自动拉取未知镜像，不删除卷。端口18080～18083只绑定127.0.0.1。

新卷初始化按V001起逐个执行SQL并记录`schema_history`校验和。已有旧阶段测试卷不能直接重跑初始化；先备份，再用迁移脚本升级。脚本不会自动删除旧库或卷。

## 3. Kubernetes首次准备

提供的MySQL清单仅面向隔离开发集群。生产应由管理员准备有备份/恢复机制的数据库、存储、TLS入口和私有镜像凭证；按实际数据库地址调整Deployment中的DB_URL及迁移Secret中的DB_HOST。

对全新的开发命名空间，可执行：

```bash
python scripts/bootstrap-microservices-k8s.py --confirm-new-namespace --enable-mock-payments
```

脚本遇到已存在的命名空间立即退出，绝不覆盖现有凭证或数据。它创建MySQL及三个数据库、DML账号、DDL迁移账号、三个应用Secret、三个迁移Secret和公钥ConfigMap，不部署业务镜像。省略`--enable-mock-payments`时关闭模拟付款。

私有GHCR镜像需在同一命名空间预先创建`registry-credentials`类型为`kubernetes.io/dockerconfigjson`的Secret；凭证不得写入清单。正式部署前验证Kubernetes节点能拉取三个服务和网关的同一SHA版本镜像。

## 4. 自动部署

仓库Actions环境`microservices`配置：

| 名称 | 类型 | 内容 |
|---|---|---|
| MICROSERVICES_DEPLOY_ENABLED | 仓库变量 | `true`启用master自动部署 |
| MICROSERVICES_KUBECONFIG_BASE64 | 环境Secret | 仅新命名空间部署所需权限的kubeconfig，经base64编码 |
| GITHUB_TOKEN | Actions自动凭证 | packages:write，用于推送同仓库GHCR镜像 |

只有verify和全部images成功后才会进入deploy。PR及非master分支不推送镜像，不部署。按共享模块影响，目前每次提交运行全部三个服务测试并构建四镜像，优先保证联动回归完整性。

手工等价命令：

```bash
bash scripts/deploy-microservices.sh ghcr.io/owner/repository <已通过测试的提交SHA>
```

脚本先检查Secret/ConfigMap，保存发布前Deployment，逐服务运行SQL迁移Job，再更新镜像和APP_VERSION，等待各Deployment就绪；任何一步失败退出非零并保存日志、事件和资源描述。发布并发由流水线concurrency串行化；禁止同时手工执行迁移。

迁移使用Vxxx文件名与SHA256记录，重复部署跳过已执行版本；修改已执行SQL会报错，应增加新的Vxxx。MySQL DDL并非事务整体可回滚，迁移失败必须保留现场、检查部分执行状态并由管理员修复，不能盲目重跑或删除history。

## 5. 失败诊断与回滚

```bash
bash scripts/collect-microservice-diagnostics.sh reports/deployment/diagnostics
kubectl -n secondhand-microservices get pods,deploy,jobs
kubectl -n secondhand-microservices get events --sort-by=.lastTimestamp
kubectl -n secondhand-microservices logs deployment/trade-service --tail=100
bash scripts/rollback-microservices.sh ghcr.io/owner/repository <之前验证通过的SHA>
```

检查顺序：镜像拉取→启动异常→SQL迁移Job→readiness→应用日志/内部调用错误→业务冒烟。liveness不依赖下游或数据库；readiness包含本服务数据库。失败不会被当作发布成功。

回滚只回应用镜像与APP_VERSION，保留数据库和上传卷；发布应采用向前兼容的扩展迁移。结构不兼容时必须先恢复备份/人工修复，不能承诺镜像回滚就能恢复数据。部署脚本保存的before.yaml用于查找真实旧版本，不自动选择latest。

## 6. 既有单体数据切换

本轮不读取、不迁移现有开发或生产数据。切换前冻结单体写入并备份；按表归属导出16张表，保留主键与跨域ID，分别导入空的对应库；初始化用户token版本、订单商品快照及存量订单的库存状态；校验行数、金额、库存、角色和历史订单；运行全部回归及人工抽检后切换网关。旧令牌建议失效并重新登录。

已有订单不能仅复制orders表后直接启用新取消逻辑：需补建trade_operations和对应库存预占状态，已扣过的库存不得再次扣减。该切换需要明确的源库快照、维护窗口与回退点，不在未知现网数据上自动执行。

## 7. 实测与未执行项

本地Compose镜像、健康/版本接口、网关三条业务流程、失败日志及回滚由本轮报告记录。Kubernetes清单通过kubectl结构校验，Shell脚本通过bash语法检查。远端推送、GHCR发布、远端CI/CD与实际Kubernetes发布本轮未执行，不能用本地报告冒充远端流水线原始报告。

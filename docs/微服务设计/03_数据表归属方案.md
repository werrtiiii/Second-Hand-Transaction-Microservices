# 数据表归属方案

> 方案日期：2026-08-28；基线提交 `fa88c48f5481a8d551fa8b2b336148fcf943ad56`。
> **只做归属和迁移设计，没有创建数据库、执行 SQL 或搬迁数据。** 当前 `db/init.sql` 与 Java `@Table` 声明共对应 16 张业务表。拟新增的表和字段在后文单独列出，不能算作现有实现。

## 1. 数据拥有权规则

| 目标服务 | 目标数据库 | 运行账号示意 | 唯一拥有的数据 |
|---|---|---|---|
| user-service | `secondhand_user` | `secondhand_user_app` | 身份、资料、地址、聊天、通知投影及身份失效状态 |
| product-service | `secondhand_product` | `secondhand_product_app` | 商品、可售库存、分类、图片、评论、收藏、举报及库存预占 |
| trade-service | `secondhand_trade` | `secondhand_trade_app` | 议价、订单、支付记录、履约、售后、评价及交易恢复任务 |

三个数据库可以位于同一个 MySQL 实例；账号和权限必须分别建立。每个运行账号仅有本库所需 DML 权限，不授予 `*.*`、其他业务库、DDL 或 GRANT OPTION。数据库变更由该服务专用迁移账号完成，应用不使用 root。密码由 Secret 注入，不写入版本库。

“拥有”包含结构变更、写入、状态推进、查询授权和审计责任。其他服务无论读还是写，都不得直接连接拥有方数据库；跨服务不建立外键、JOIN、视图或触发器。用户 ID、商品 ID 等可在其他服务保存为逻辑引用，但不是远程 JPA 实体关联。

## 2. 现有 16 张业务表的逐表归属

### 2.1 用户服务：4 张

| 表 | 业务含义 | 目标库与唯一拥有服务 | 关系及其他服务访问方式 |
|---|---|---|---|
| `users` | 账号、昵称、角色、状态、密码哈希、联系方式与头像 | secondhand_user / user-service | 外域仅存 userId；公开摘要走 INT-U-02；令牌和禁用状态走 INT-U-01；禁止输出密码哈希 |
| `user_identities` | 手机号/邮箱登录标识及其所属账号 | secondhand_user / user-service | user_id → 本库 users；仅认证业务读取，不对商品/交易提供原始表查询接口 |
| `user_addresses` | 用户收货地址、标签和默认地址 | secondhand_user / user-service | user_id 是本域引用；交易下单用 INT-U-03 校验本人地址，再保存订单快照 |
| `chat_messages` | 商品会话、发送人、接收人、内容、时间和已读状态 | secondhand_user / user-service | sender_id/receiver_id 为本域用户；product_id 为商品逻辑引用；商品摘要通过 INT-P-01/02 取得 |

### 2.2 商品服务：6 张

| 表 | 业务含义 | 目标库与唯一拥有服务 | 关系及其他服务访问方式 |
|---|---|---|---|
| `products` | 商品标题、描述、卖家、分类、价格、数量及上下架状态 | secondhand_product / product-service | category_id 为本域关系；seller_id 为用户逻辑引用；交易仅通过 INT-P-01/03/04/05/06 获取商品和操作库存 |
| `product_images` | 商品图片、缩略图、排序、创建时间 | secondhand_product / product-service | product_id 为本域关系；图片必须归属当前商品；图片文件也由商品服务独占写入 |
| `categories` | 分类名称、父子层级和排序 | secondhand_product / product-service | 分类层级在本域内处理；不与用户地区数据混用 |
| `favorites` | 用户与收藏商品的关系 | secondhand_product / product-service | product_id 本域、user_id 外域；保留用户商品组合去重；`/api/users/favorites` 由商品服务实现 |
| `comments` | 商品评论、作者和发表时间 | secondhand_product / product-service | product_id 本域、user_id 外域；作者摘要用 INT-U-02；评论通知通过 outbox 投递 |
| `reports` | 商品举报、举报人、审核状态、处理人和处理备注 | secondhand_product / product-service | product_id 本域；reporter_id/handled_by 为用户逻辑引用；审核与商品状态在本域处理，通知由事件生成 |

### 2.3 交易服务：6 张

| 表 | 业务含义 | 目标库与唯一拥有服务 | 关系及其他服务访问方式 |
|---|---|---|---|
| `offers` | 报价金额、买卖双方、报价状态和关联订单 | secondhand_trade / trade-service | order_id 本域；product_id、buyer_id、seller_id 外域；接受报价后使用统一库存预占流程 |
| `orders` | 订单金额、状态、买卖双方、商品引用、收货快照及关键时间 | secondhand_trade / trade-service | product_id、buyer_id、seller_id、address_id 为外域逻辑引用；不按地址 ID 动态覆盖历史订单地址 |
| `order_events` | 订单状态变化和事件描述 | secondhand_trade / trade-service | order_id 本域；消息中心不得直接查询；此表不是可靠投递队列，outbox 另建 |
| `shipments` | 运单、承运人、物流状态与订单关联 | secondhand_trade / trade-service | order_id 本域；物流接口和物流适配器归交易服务；当前 Mock 并非独立微服务 |
| `after_sale_requests` | 售后类型、退款金额、举证、退货、仲裁、运费责任及状态 | secondhand_trade / trade-service | order_id 本域；买卖双方和操作者用户标识外域；售后不得直接更新用户或商品表 |
| `ratings` | 订单评价、评价人、卖家、评分、评语和时间 | secondhand_trade / trade-service | order_id 本域；product_id 为商品逻辑引用，reviewer_id/seller_id 为用户逻辑引用；卖家评分摘要通过 INT-T-03 提供 |

**外键现状核对：** 当前初始化脚本中显式声明的外键是 `user_identities.user_id → users.id`，两表迁入同一个用户库，因此保留该库内关系。其余 ID 字段不能被描述为已经存在的数据库外键；它们按现有逻辑关联处理。后续可以在清理孤儿数据后增加必要的同库约束，但不得新增跨库约束。

## 3. 拟新增的支撑表：7 张物理表

下列均为方案，不是当前已有表；`outbox_events` 在商品库和交易库各有一张，由各自服务独占管理，绝不是两个服务共用一张表。

| 目标库 | 拟新增表 | 最小职责与关键字段 | 幂等、唯一性及恢复规则 |
|---|---|---|---|
| secondhand_user | `notifications` | source_service、event_id、recipient_id、event_type、aggregate_id/version、payload、occurred_at、received_at | UNIQUE(source_service,event_id,recipient_id)；保存载荷摘要检测同键异内容；通知投影不改写业务事实 |
| secondhand_user | `user_security_state` | user_id、token_version、revoked_before、updated_at | user_id 唯一；踢下线/改密推进失效版本；多实例共享本库状态；登录后令牌携带新版本 |
| secondhand_product | `inventory_reservations` | operation_id、order_id、product_id、quantity、status、payload_hash、product_snapshot、version、created_at、updated_at | operation_id 唯一；同订单同商品绑定唯一；数量扣减与记录同事务；允许无 product_id 的提前释放墓碑，迟到预占不得扣库存 |
| secondhand_product | `outbox_events` | event_id、event_type、aggregate_id/version、payload、status、attempts、next_retry_at、last_error、locked_until | 与评论/举报等变更同事务；重启后继续投递；成功响应后标记已投递；失败持久化退避、告警和人工重放 |
| secondhand_trade | `trade_operations` | operation_id、order_id、actor_id、operation_type、idempotency_key、payload_hash、status、result、attempts、next_retry_at、last_error、version | 用户/操作/幂等键组合唯一；保存创建、库存确认和释放任务；用租约或条件更新防止多工作进程并发执行 |
| secondhand_trade | `outbox_events` | 与商品库 outbox 同类的投递字段 | 只保存交易/售后通知；与订单状态/事件同事务；不读写商品库 outbox |
| secondhand_trade | `payments` | payment_no、order_id、buyer_id、amount_cent、method、status、idempotency_key、created_at、updated_at | payment_no 唯一；校验支付号/订单/买家绑定；状态条件更新防止重复支付或退款；第一版仍是 Mock，不宣称已接真实资金系统 |

拟新增表合计：用户 2 张、商品 2 张、交易 3 张。实施后在不删除原表的前提下共 23 张物理表；实施时须用迁移脚本重新核对，不能仅凭本文断言结构已存在。

## 4. 拟调整的现有字段与快照

| 表 | 目标调整 | 原因及约束 |
|---|---|---|
| `orders` | 在 orders.status 和 Java OrderStatus 中增加 CREATING、CREATE_FAILED；补偿任务状态另存 trade_operations，不冒充支付状态 | 创建结果未知时可返回持久化订单 ID，不返回一个不存在的成功订单；原有待支付/待发货状态只在条件满足后推进；前端和测试需识别新增状态 |
| `orders` | 增加 product_title、product_cover_url、product_version、snapshot_source、snapshot_captured_at 等快照字段；保留原有 amount_cent 和 receiver_* | 商品后续改名、下架或用户改地址不改变历史订单；收货信息修改仍只能走允许状态下的订单接口 |
| `products` | 增加 version；明确人工/审核下架与售罄下架的区分字段 | 乐观并发校验；释放库存仅增加可售数量，不能擅自撤销审核下架；存量无法判定原因的下架商品默认不自动重上架 |
| `chat_messages` | 可增加 product_title_snapshot、product_cover_snapshot，或使用独立会话展示缓存 | 商品删除/不可用时仍可展示历史会话，但不能把旧快照视为当前可交易状态 |

订单存量快照必须区分来源：只能从迁移时现存商品回填的字段标记为 `MIGRATION_CURRENT`，不能冒充成交时原始信息。已经缺失的商品保留 ID 和“历史信息不可恢复”的明确标记；金额和已有地址使用订单原字段，不用商品现价重算。

存量 `orders.address_id` 可能为空，现有下单流程虽然接收 addressId，但不能据此认定全部订单都已维护该关联；以现有 receiver_* 快照为准。

第一版库存数量按每单一件处理。库存状态流转及恢复细节以 [内部接口清单](02_服务接口清单.md) 的 INT-P-03～06 为准。是否把退货重新计入可售库存是独立业务判断，不能在所有退款成功时自动加库存。

## 5. 跨服务数据访问矩阵

| 消费服务 | 所需数据或动作 | 唯一拥有服务 | 允许方式 | 禁止方式 |
|---|---|---|---|---|
| 商品、交易 | 用户有效性、角色 | 用户 | INT-U-01 | 读取 users 或复制身份 Repository |
| 商品、交易 | 最小公开用户摘要 | 用户 | INT-U-02 | 直接读取用户库、返回密码/私密资料 |
| 交易 | 买家选用的地址 | 用户 | INT-U-03 + 委托身份校验 | 仅凭 addressId 读取任意地址、跨库关联地址表 |
| 用户 | 评分、交易待办、交易统计 | 交易 | INT-T-01/02/03 | 直接查 ratings、orders、offers |
| 用户 | 商品摘要与商品统计 | 商品 | INT-P-01/02/07 | 直接查 products 或给用户库建立商品表视图 |
| 交易 | 商品详情、库存 | 商品 | INT-P-01/03/04/05/06 | 直接调用 ProductRepository、跨库 JOIN、直接 UPDATE quantity |
| 商品对账任务 | 订单是否允许释放库存 | 交易 | INT-T-04 | 直接读取 orders；看到查询超时就释放 |
| 商品、交易 | 用户通知投递 | 用户 | 本库 outbox → INT-U-04 → notifications | 直接插入用户库；进程内队列成功即当送达 |

每个内部查询仅返回完成任务所需的最小字段。公开卖家资料可包含评分，但内部用户摘要必须是只读叶子接口，不能反向聚合交易评分，避免循环依赖。

## 7. 数据迁移顺序（实施方案，不是执行记录）

1. 固定改造前 Git 提交，备份单体数据库及上传文件，在隔离环境做恢复验证。当前 `db/init.sql` 包含 DROP TABLE 和种子数据，不能直接向生产已有库重放。
2. 分别建立三个目标库、运行账号和迁移账号，执行各服务的版本化建表/变更脚本。确认表名、字符集、时区、索引、枚举和约束与源码一致；数据库 schema 自动更新不承担正式迁移职责。
3. 最小方案采用维护窗口暂停写入，在一致快照上按表归属导出导入；保留主键和 AUTO_INCREMENT 后续范围，防止用户/订单逻辑引用被重编号。
4. 在受控迁移任务中验证跨域 ID、孤儿记录、金额和状态数量；迁移任务的临时权限不是运行服务的跨库权限，完成后撤销。不得通过“永久同步脚本”让三个服务继续共享旧业务表。
5. 回填订单/聊天展示快照、必要的历史通知投影；记录来源、批次和水位。历史通知通过拥有方导出的受限 DTO 转换，不能让用户服务在运行时直接读订单和举报库。
6. 校验每表总数、主键集合/分段摘要、业务状态分布、订单金额汇总、文件 URL 可用性；确认旧库和新库均有可恢复备份。仅比较行数不足以证明数据正确。
7. 配置各服务只连接自己的库，启动后执行数据库权限反向测试、完整 API 回归和七个业务场景 E2E，再切入口路由。关闭旧后端写入口，避免双写和库存重复扣减。
8. 观察期保留旧库只读备份。新系统已产生写入后，不能简单把路由切回旧库当成安全回滚；须暂停写入，评估增量回迁或修复向前推进。删除旧库需另行批准，本次不执行。

## 8. 数据隔离与一致性验收

| 检查项 | 通过标准 |
|---|---|
| 表归属完整性 | 16 张现有表与 DDL、Entity 一致，每表恰好一个拥有服务；新增表单独清点 |
| 数据库账号隔离 | 每个运行账号读写自己所需表成功；SELECT/INSERT/UPDATE/DELETE 其他业务库均被 MySQL 拒绝；无跨库权限或 root 连接 |
| 代码访问隔离 | 交易服务没有 ProductRepository，用户服务没有 Order/Offer/Rating/Report/Comment Repository；无跨库 SQL、视图、触发器或共享实体关联 |
| 幂等与并发 | 重复下单不重复建单或扣库存；并发争抢最后一件不会超卖；重复释放不会重复加库存；迟到预占不会突破释放墓碑 |
| 状态未知恢复 | 超时后按原操作号查结果；进程重启后继续处理确认/补偿；未知订单不得自动释放库存 |
| 下架保护 | 取消订单释放库存后，不把被人工/审核下架的商品自动重上架 |
| 通知一致性 | 业务提交后崩溃仍能补发；重复投递不重复显示；乱序旧事件不覆盖新投影；失败可告警重放 |
| 隐私和历史数据 | 地址只对本人授权；令牌/密码不落日志；订单快照不受商品和地址后续修改影响 |
| 迁移可核对 | 行数、主键、关键字段、金额、状态和文件均有校验记录；快照回填不能假称历史原始数据 |

本次提供的 [核对清单.py](核对清单.py) 只核对源码中的 API/表与文档清单是否一致，不会访问数据库，也不代表上述运行期验收已经通过。

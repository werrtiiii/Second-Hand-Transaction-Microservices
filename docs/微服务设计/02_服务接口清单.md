# 服务接口清单

> 设计版本：2026-08-28。基线 `fa88c48f5481a8d551fa8b2b336148fcf943ad56`。本文是拟拆分方案，不表示三个服务或内部 API 已经存在。

## 1. 范围与统计

按当前 Controller 的 HTTP 方法和完整路径去重，共 **104 个现有业务 API**；包括匿名、登录、管理端、旧版兼容和 Mock 接口。不是“104 个已通过测试的接口”。SPA 页面路由、静态文件、框架提供的 Actuator/OpenAPI 路径不计入这个数字。

| 目标服务 | 现有 API 数 | 拟新增内部 API 数 |
|---|---:|---:|
| user-service | 28 | 4 |
| product-service | 25 | 7 |
| trade-service | 51 | 4 |

现有 API 保留路径、主要请求字段和响应业务含义；跨域路径按实际业务路由，不按 URL 第一段机械分配。表内“目标权限”是改造后的要求，不能当作当前代码已实施的权限保证。

## 2. 通用契约

- 外部响应沿用 `ApiResponse<T>`：成功 `{ "success": true, "data": ... }`，失败 `{ "success": false, "error": { "code": "...", "message": "..." } }`。空字段可能按现有 Jackson 配置省略。接口表响应类型中的 `T` 是现有类型；拆分后用专属 DTO 保持 JSON 字段，不跨服务共享 JPA Entity。
- 普通同步成功保持现有 HTTP 状态（注册 201，其余通常 200）。目标错误统一为 400 参数错误、401 未登录、403 无权限、404 不存在、409 状态或幂等冲突、429 限流、503 服务依赖不可用、504 上游超时。当前部分接口返回 HTTP 200 + success=false，改造时需要同步客户端与测试，本文没有声称现状已经统一。
- 请求参数表直接取自当前 Java 声明：`@PathVariable` 是路径参数，`@RequestParam` 是查询参数（MultipartFile 除外），`@RequestBody` 是 JSON；`required=false`、defaultValue 和约束按原声明保留。MultipartFile 使用 multipart/form-data。身份参数不从请求体取得。
- 金额均用整数分，ID 使用现有 Long 语义；分页参数和默认值以各行声明为准。时间在迁移时明确现有 LocalDateTime 的 Asia/Shanghai 解释，不能直接把存量时间当 UTC；内部新事件时间采用带偏移 ISO 8601。
- 外部使用用户 Bearer JWT；每个服务自行校验令牌和资源归属。用户状态/强制下线通过 INT-U-01 校验，不共享 users 或进程内黑名单。默认先不缓存有效性结果，依赖故障时受保护操作拒绝执行。
- 写入型跨服务接口使用 Idempotency-Key；幂等作用域包含调用服务、业务操作和用户/订单标识，同键不同载荷返回 409。日志记录 requestId/traceId，不记录密码、令牌或完整地址。
- 下单/接受报价若无法同步确定结果，目标允许 202 + 已持久化的订单 ID/创建状态，客户端使用现有 GET /api/orders/{id} 查询；需要客户端适配，不能声称完全无感兼容。超时不意味着操作未发生，不允许换新幂等键盲重试。

## 5. 拟新增内部接口（15 个，均未实现）

内部入口固定 `/internal/v1/**`，通过 Kubernetes 服务 DNS 调用，公网入口显式拒绝。必须新增内部 SecurityFilterChain：校验独立服务凭证的签名、到期时间、audience、调用服务 allowlist 和 scope。不能依赖现有非 /api/** 默认放行规则。

服务身份与用户身份分开：Authorization 携带短期服务凭证；需要用户/管理员权限的委托操作另外携带 X-User-Token，接收端校验真实令牌与路径 userId，不能信任任意 X-User-Id。网关必须删除外部伪造的内部身份头。后台库存补偿和 outbox 投递使用专属 scope 和持久化业务记录，不依赖用户令牌长期有效。

以下内部查询都是“叶子接口”：只读取本服务数据，不再调用别的服务做聚合。禁止用公开的卖家资料接口代替 INT-U-02，否则可能形成“用户资料→评分→用户资料”的循环调用。

## 6. 关键内部契约示例

以下 JSON 是目标协议示例，不是已存在接口的实际返回。商品数量当前按每单一件处理，未来多件购买需另行变更契约。

### 6.1 库存预占

```http
POST /internal/v1/inventory/reservations
Authorization: Bearer <trade-service-credential>
Idempotency-Key: order-create-10001
Content-Type: application/json

{"operationId":"order-create-10001","orderId":10001,"productId":20001,"buyerId":301,"expectedSellerId":302,"quantity":1,"expectedProductVersion":7,"pricingMode":"LIST","expectedListPriceCent":12000}
```

LIST 模式要求原价与版本匹配；NEGOTIATED 模式只允许交易服务在本地核验已接受报价后发起，成交金额取交易库报价，不能接受浏览器提供的任意议价金额。商品服务检查卖家、状态、库存和商品版本，在同一本地事务中写 reservation 并扣一次可售库存。响应携带这次预占时的商品快照，供订单保存。

库存状态为 RESERVED → CONFIRMED，创建失败或有效取消可转为 RELEASED。confirm 不二次扣库存，release 仅首次恢复数量。release 先于 reserve 到达时写入 RELEASED 墓碑；同 operationId 后到的 reserve 返回 409。第一版不盲目用 TTL 自动释放，对账通过 INT-T-04 确认订单状态；未知结果只重试与告警。已付款订单不能因为调用超时释放库存。

### 6.2 通知事件

```json
{
  "eventId": "report-701-handled-v2",
  "eventType": "REPORT_REVIEWED",
  "aggregateId": "701",
  "aggregateVersion": 2,
  "recipientIds": [301, 302],
  "occurredAt": "2026-08-28T12:00:00+08:00",
  "payload": {"productId": 20001, "status": "HANDLED", "title": "举报处理结果", "content": "请查看商品处理结果"}
}
```

商品服务可发送 COMMENT_CREATED、REPORT_REVIEWED；交易服务可发送 ORDER_STATUS_CHANGED、AFTER_SALE_STATUS_CHANGED。用户服务从经过认证的调用方确定 sourceService，不接受外部自报来源。以 (source_service,event_id,recipient_id) 去重并比较载荷摘要；来源版本用于拒绝过期覆盖。发送方业务变更与 outbox 记录同事务，用户服务确认持久化后发送方才标记成功；失败按退避策略重试，耗尽后持久化告警与人工重放，不丢弃。

订单、举报和评论详情仍归原业务服务；通知表只保存通知投影及必要的展示快照，不能成为新的订单或举报事实表。历史消息从各拥有服务导出受限通知 DTO 进行回填，不让用户服务直连其他库。

## 8. 改造验收规则

1. 104 个现有 API 每个都能定位唯一目标服务；每个服务提供自己的 OpenAPI，实际 RequestMapping 与清单再次比对。
2. 每个公开 API 关联成功、权限/参数/业务异常测试；兼容和 Mock 入口也明确测试环境与关闭策略。这里的清单完整性校验不等于 API 测试覆盖率。
3. 15 个内部接口建立契约测试；验证凭证缺失、错误调用服务、伪造用户、超时、重复请求、同键异载荷和乱序请求。
4. 聚合字段不可用时第一版返回明确 503，不能把错误当空列表/零值；聊天中的历史商品展示可使用已记录快照，但必须标记当前商品状态未知。
5. 所有目标安全收紧项（auth/me、结算、售后管理员旧入口、物流访问、报价/支付/评价归属）由迁移任务实施并验证；本次只记录方案，未修复现有代码。

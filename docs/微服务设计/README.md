## 核心统计

| 服务 | 现有公开业务 API | 现有业务表 | 拟新增内部 API |
|---|---:|---:|---:|
| user-service | 28 | 4 | 4 |
| product-service | 25 | 6 | 7 |
| trade-service | 51 | 6 | 4 |
| 合计 | **104** | **16** | **15** |

这里的“公开业务 API”指现有 `/api/**` Controller 接口，包含匿名、需登录、管理端、旧版兼容和 Mock 接口，不等于所有接口都匿名开放。SPA 路由、静态文件、框架生成的 Actuator/OpenAPI 路径不计入 104。既有 API 的方法和路径按源码保留；目标权限、状态和内部契约是后续改造要求。

## 设计中的关键决定

- `/api/users/{sellerId}/products` 属于商品服务，`/api/users/{sellerId}/sold` 和 `/api/users/{userId}/rating` 属于交易服务，不能按 URL 前缀整包搬迁。
- 管理员功能按业务服务分配；用户服务只保留少量只读聚合入口，不拥有其他服务的表。
- 用户、商品、交易分别使用独立数据库和账号；可以共用一个 MySQL 实例，不能跨服务直读写或联表。
- 交易与商品之间采用幂等库存预占/确认/释放及持久化恢复任务；通知采用本库 outbox 和用户库通知投影。
- 内部 API 需要专门的服务认证、调用方权限和必要的用户委托校验，不能沿用当前非 `/api/**` 默认放行策略。
- 目标要求收紧的权限和拟新增的持久化表均明确标为待实施，没有把当前缺口描述成已经修复。

## 如何复核

在项目根目录执行：

```powershell
python "docs/微服务设计/核对清单.py"
```

需要刷新核对结果文件时执行：

```powershell
python "docs/微服务设计/核对清单.py" --report
```

检查范围：104 个方法/路径无重复或遗漏、原方法签名未漂移、目标服务有效、16 张表与 DDL 和 Entity 一致、逐表唯一归属、内部接口编号和路径一致、图源与正文图一致。

这个脚本是针对当前直接声明 Mapping 和 Table 的源码结构进行静态核对，不启动 Spring，也不检查运行时授权、并发正确性或接口测试覆盖率。后续实现应结合各服务 OpenAPI 和真实 HTTP 测试重新验收。

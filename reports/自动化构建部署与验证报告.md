# 微服务自动化构建、部署与验证报告

生成时间：2026-09-01。本轮在本地完整执行"提交→构建→测试→镜像→部署→可观测→故障诊断→回滚恢复"闭环，所有数字来自本轮实测，不以远端流水线结果冒充本地证据。

## 1. 自动构建与自动部署机制

流水线 `.github/workflows/microservices-ci.yml`，`push`/`pull_request`/手动触发，concurrency 串行化：

| 阶段 | 内容 | 失败行为 |
|---|---|---|
| verify | 边界检查 → 后端全部 API/数据库隔离/七类 E2E（`mvn clean verify`，Testcontainers 临时 MySQL）→ 前端测试与生产构建 → 汇总报告完整性校验 | 不构建镜像、不部署，原始报告仍归档 |
| images | 四镜像（user/product/trade/gateway）按提交 SHA 构建，GHA 缓存加速；仅 master push 推送 GHCR | verify 未通过则整组跳过 |
| deploy | 仅当 `vars.MICROSERVICES_DEPLOY_ENABLED == 'true'` 且 master push；使用环境 `microservices` 的专用 kubeconfig；`scripts/deploy-microservices.sh` 先跑 SQL 迁移 Job 再更新镜像与 `APP_VERSION`，等待就绪 | 退出非零、保存部署现场工件、清理凭证；`collect-microservice-diagnostics.sh` 收集 pods/events/logs |

## 5. 一次部署失败的现场诊断记录

**场景**：构造坏版本 `dev-004`（用 `tests/deployment/failure-gateway.Dockerfile` 在正常网关镜像上注入非法 nginx 模板 `intentional_invalid_directive;`，三业务镜像沿用 dev-003 打同版本标签），模拟"一次错误提交被发布"。

1. 部署 `deploy-microservices-local.ps1 -Version dev-004` → **失败，退出码 1**："网关业务验证未通过"。部署脚本不把失败当成功：readiness 三服务虽 UP，但网关冒烟不通过即判定发布失败并自动保存现场 `reports/local-runtime/deployment-failure.log`。
2. `docker compose ps` → **gateway 容器 `Restarting (1) 8 seconds ago`（crash loop）**，mysql healthy、三个业务服务正常 → 问题定位于网关镜像本身，而非数据库或业务服务。
3. `docker compose logs gateway` → 根因：`nginx: [emerg] unknown directive "intentional_invalid_directive" in /etc/nginx/conf.d/default.conf:1` —— 镜像内 nginx 配置模板含非法指令，envsubst 渲染后 nginx 启动即退出。
4. 处置：`rollback-microservices-local.ps1 -Version dev-003` 回滚到已验证版本 → 冒烟 PASS，`/actuator/info` 三个服务恢复 `dev-003`，网关 200。坏镜像与数据卷均保留，用于复盘。

**检查顺序**（与 `docs/微服务部署与回滚.md` 一致）：业务冒烟失败 → 容器状态 → 容器日志定位镜像缺陷 → 回滚已验证版本。远端 Kubernetes 场景等价命令：`collect-microservice-diagnostics.sh` 自动收集 `resources.txt`、`events.txt`、各服务 `describe` 与日志、迁移 Job 日志。

## 6. 结论

- 提交后自动化"构建→测试→镜像→部署"链路在 CI 定义与本地实测中均成立；任一测试失败不会发布或部署镜像。
- 104 个公开接口全部有 API 测试与成功 HTTP 证据；七类业务场景完成端到端回归（115 项后端用例 + 25 项前端用例全通过）。
- 日志、健康、就绪、版本均可现场查验；一次真实失败发布已按标准流程诊断定位并回滚恢复。

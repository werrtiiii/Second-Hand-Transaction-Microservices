# 单体版与微服务版性能对比实验报告

## 1. 实验目的

在同一台机器、同一批业务数据、同一份压力脚本下，对单体版与拆分后的微服务版进行不少于 3 次的重复压力测试，记录并比较并发数、请求总数、吞吐量、平均响应时间、P95、错误率、CPU 和内存。本实验不预设微服务一定更快，只有实测数据支持时才表述为性能提升。

## 2. 实验时间和环境

- 实验日期：2026-09-01
- 操作系统：Windows 11 10.0.22631
- CPU：AMD64 Family 25 Model 117，16 个逻辑处理器
- 数据库：本机 MySQL 8.0，同一个 MySQL 实例
- 压测工具：Grafana k6，通过 Docker 容器运行
- 单体入口：http://host.docker.internal:8088
- 微服务入口：http://host.docker.internal:18080
- 微服务运行方式：本机原生 Java 进程和 Node API 网关
- Kubernetes HPA：本实验未启用，三个微服务各保持一个实例

单体测试统计一个 Java 后端进程。微服务测试统计 user-service、product-service、trade-service 三个 Java 进程和 Node API 网关的合计值，前端进程不计入。CPU 以一个逻辑核心为 100% 统计，因此 200% 表示合计使用约两个逻辑核心。

## 4. 压测接口

统一脚本轮询以下 3 个匿名只读接口：

| 接口 | 所属领域 | 微服务目标 |
| --- | --- | --- |
| GET /api/products?page=0&size=20 | 商品列表 | product-service |
| GET /api/regions | 地区列表 | user-service |
| GET /api/users/2/rating | 用户评分 | trade-service |

正式测试前，两版三个接口均经过 HTTP 200 和 success=true 预检。

## 5. 压测条件

每次测试条件完全一致：

- 并发数：50 VU
- 正式持续时间：45 秒
- 每个版本正式运行次数：3 次
- 每次正式测试前预热：10 VU，10 秒
- 接口分配：按全局迭代次数轮询三个接口
- 错误率阈值：小于 1%
- P95 阈值：小于 1500 ms
- 业务检查通过率阈值：大于 99%

为降低固定顺序产生的温度、JIT 和缓存偏差，执行顺序为：

1. 单体第 1 次，微服务第 1 次
2. 微服务第 2 次，单体第 2 次
3. 单体第 3 次，微服务第 3 次

每次测试都重新启动目标版本并单独预热。两套后端不会同时运行，避免互相争抢 CPU 和内存。

## 8. 结果分析

本次只读接口测试中，微服务平均吞吐量比单体高 2.62%，差异不大。三次微服务吞吐量的样本标准差约 9.20 req/s，单体约 55.19 req/s，微服务吞吐量更稳定。

微服务平均响应时间高 3.77%，P95 高 6.36%。请求需要先经过 Node API 网关，再进入具体服务；三个独立 JVM、独立连接池和独立运行时也会带来额外调度与内存开销。即便所选接口不发生跨服务写事务，网关和进程边界仍会产生少量延迟。

资源成本差异明显。单体只有一个 JVM，微服务需要三个 JVM 和一个网关进程，即使某些服务负载较低，也要保留各自的堆、元数据、线程、连接池和框架对象。因此微服务平均工作集约为单体的 2.74 倍，平均 CPU 合计约为 3.99 倍。微服务峰值 CPU 较高还受到每轮重启后的多个 JVM JIT 编译影响。

所以本实验不能得出“微服务全面提升性能”的结论。准确结论是：

- 两版在 50 并发下均稳定通过，错误率为 0%。
- 微服务吞吐量略高 2.62%，属于接近水平。
- 微服务平均延迟和 P95 略高。
- 微服务消耗更多 CPU 和内存。
- 微服务改造的主要收益是服务边界、独立构建部署、故障隔离和独立扩缩容，而不是单机资源效率。

## 9. 实验局限

1. 数据量较小，只有 3 个用户、2 个商品和 2 个订单。
2. 本轮只测试匿名只读接口，没有覆盖登录、写入、事务和跨服务补偿。
3. GET /api/regions 响应约 94 KiB，网络传输占比较高。
4. k6 和应用运行在同一台机器，虽然应用 CPU 只统计目标进程，但压测端仍占用整机资源。
5. 每轮预热 10 秒不能完全消除 JVM JIT 差异。
6. 本轮是本地固定实例对比，不代表 Kubernetes HPA 扩容后的容量上限。
7. 只有 3 次重复测试，适合课程实验，不等同于生产容量评估。

## 10. 自动复原结果

实验脚本在 finally 中执行以下操作：

1. 结束当前 k6 容器；容器使用 --rm，不保留压测容器。
2. 停止单体 Java 进程，确认 8088 不再监听。
3. 停止测试过程中的微服务实例。
4. 使用既有 JAR 和前端依赖重新启动微服务。
5. 验证三个微服务、网关和前端均为 UP。
6. 验证三个实验接口重新通过微服务网关访问。
7. 删除本次脚本创建的唯一临时数据库。
8. 清除实验进程中的 MySQL root 密码引用。
9. 保持 MySQL 运行，使微服务可以继续访问数据库。

## 11. 手工复原步骤

如果脚本被断电或强制终止，可按以下步骤复原。

### 11.1 停止残留单体

    $connection = Get-NetTCPConnection -LocalPort 8088 -State Listen -ErrorAction SilentlyContinue
    if ($connection) {
        Stop-Process -Id $connection.OwningProcess -Force
    }

### 11.2 停止残留 k6 容器

先查看：

    docker ps --filter ancestor=grafana/k6:latest

确认是本实验容器后，再使用其容器 ID：

    docker stop <容器ID>

### 11.3 清理临时数据库

读取对应实验目录的 source.json，取得 temporaryDatabase。名称必须以 secondhand_benchmark_perf_ 开头，并与 source.json 完全一致。

先查看，不直接删除：

    mysql -uroot -p -e "SHOW DATABASES LIKE 'secondhand_benchmark_perf_%';"

确认精确名称后：

    mysql -uroot -p -e "DROP DATABASE secondhand_benchmark_perf_年月日时分秒;"

不要删除 secondhand、secondhand_user、secondhand_product 或 secondhand_trade。

### 11.4 重启微服务

    cd D:\OneDrive\Desktop\Second-Hand-Transaction-Microservices
    .\scripts\stop-microservices-native.ps1
    .\scripts\start-microservices-native.ps1 -SkipBuild -SkipNpmInstall -Version performance-comparison

### 11.5 验证复原

    .\scripts\status-microservices-native.ps1

    Invoke-WebRequest 'http://127.0.0.1:18080/api/products?page=0&size=20'
    Invoke-WebRequest 'http://127.0.0.1:18080/api/regions'
    Invoke-WebRequest 'http://127.0.0.1:18080/api/users/2/rating'

预期五个组件均为 UP，三个接口均返回 HTTP 200。
